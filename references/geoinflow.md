# 可选原版 GEOInflow 接入与使用

本文件仅在用户明确选用原版 GEOInflow 时适用。默认内置监测见 native-monitor.md，不需要执行本文的环境安装。GEOInflow 独立部署、独立登录、按网站权限读取。官网使用 H5 + 原生 PHP + MySQL；GEOInflow 使用自身服务与数据库。

官网侧负责公开目录、日志接入条件及管理员可见的本站监测入口。身份识别、访问统计、覆盖和风险分析直接使用 GEOInflow。

采用 GEOInflow 原项目及其官方部署流程。Skill 负责获取匹配版本的源码、准备环境配置、部署、接入和核对结果；不让模型重新生成它的全部模块，也不将其改写为 PHP/MySQL 系统。需要二次开发时另按明确需求处理。

执行顺序为：选择已有实例或新部署 → 获取并核对源码版本 → 检查目标环境 → 官方部署与健康检查 → 首次登录 → 本站目录和日志接入 → 回读及交接。复用已有实例时不重复获取或安装源码，只记录实际版本及可核对范围。

## 随建站部署 GEOInflow

同一个 Skill 可以完成官网与 GEOInflow 的部署和接入。两套服务可在资源足够的同一台服务器运行，也可分别部署；官网继续使用 PHP/MySQL，GEOInflow 使用所选版本要求的应用、PostgreSQL、Redis 与后台处理服务，不共用官网数据库。

先按任务选择路径：

| 条件 | 执行动作 |
|---|---|
| 已有可用且获准使用的实例 | 核对版本、健康和本站权限，复用实例并建立或选中本站；不为接一个官网重装、升级或重置实例 |
| 没有实例，已有明确的部署目标与授权 | 检查运行条件，按下面流程实际部署，再完成本站目录和日志接入；不能只留下一个监测链接 |
| 当前只做 Skill/页面审阅，或用户暂缓监测 | 保留部署规则或与实际项目对应的部署文件，不安装运行环境、不启动监测服务，状态记未执行 |
| 已要求部署，但缺主机、必要权限或运行条件 | 列具体缺口及解决办法，询问必要的目标或权限信息；官网可独立继续，不因没有现成实例就放弃可实施的新部署 |

建站并部署监测的指令可覆盖指定环境内的初始化、健康检查和本站接入，条件齐备按已有授权连续完成。购买主机、付费供应商服务、修改未授权域名或接管其他实例需明确范围，不能由“建站”自行推定。普通 PHP 虚拟主机不能直接运行整套 GEOInflow，应复用外部实例或准备支持其运行环境的目标。

### 前置条件与阻塞处理

监测环境检查应在官网实现前或并行准备阶段完成，不能等到交付时才发现运行环境缺失。Windows 分别核对 WSL 是否安装、Linux 发行版是否可运行、Docker CLI、Compose、守护进程与 context；仅存在 wsl.exe 或安装器不算环境就绪。保留可读错误及退出状态，不把权限拒绝误判为软件未安装。

安装器、WSL 系统功能、容器运行时和虚拟磁盘可能超出用户限定的项目目录。先核对授权范围；需扩展时给出具体安装对象、存储位置及可能的重启需求，完成源码固定和配置准备后再询问。不得为了避开环境要求改写 GEOInflow、绕过锁工具或删除原数据库。

本机受控预览站与公网正式站分别登记。预览 sitemap 按禁止索引规则保持为空；需要验证目录导入时，使用单独标明“本机预览”的私有目录包并匹配本地站点，不将其放入公开目录。日志未具备时保持日志接入未完成，不能拿官方示例数据补齐企业数据。

### 获取源码与固定版本

原项目地址为 `https://github.com/yaojingang/GEOInflow.git`。新部署使用该仓库中选定的完整源码，放在获准部署工作区的独立目录，与官网源码、Skill 目录和现有实例分开。只完善 Skill 或部署方案时写清步骤与待填目标，不下载依赖、构建镜像或启动服务。

1. **选择具体提交。** 用户已指定版本时先确认它对应的实际 Git 引用与兼容条件；未指定时查看官方可用版本与部署文档，选择适合本项目的提交并记录完整 commit SHA。不能把界面显示版本当成一定存在的 Git 标签，也不能只记 `main` 或 `latest` 作为可复现版本。
2. **获取原项目。** 优先从官方仓库 clone 到不存在的目标目录，检出选定提交。没有 Git 时可取得该完整提交对应的官方源码归档，核对下载域名、文件内容和解压路径，解压到新的独立目录。下载失败说明具体原因，不用搜索到的不明安装包替代原项目。
3. **复用已有源码。** 先只读检查 origin、HEAD、工作树差异及现有配置用途。能确认来源且符合所选提交的干净源码可复用；有定制或未提交修改时保留原目录，另取干净副本，不能执行 reset/clean 覆盖用户工作。没有源码或版本证据的运行实例可以按权限接入，但记录版本未核实，不擅自重装。
4. **核对完整性。** 检查同一提交的部署脚本、产品 Compose、Dockerfile、package.json、依赖锁文件、迁移、文档以及 LICENSE/THIRD_PARTY_NOTICES；依赖文件名以实际仓库为准。Git 检出后核对 HEAD 与目标提交一致，记录工作树状态。归档方式记录完整提交、官方来源 URL、下载时间和本地 SHA-256；本地哈希仅供后续一致性核对，没有官方签名或校验清单时不能称已完成发布者签名验证。
5. **保留许可与版本依据。** 原项目的版权、许可证、第三方声明和所需署名随源码或镜像保留。交接的来源记录可命名为 `geoinflow-source.json`，至少包含仓库地址、提交、获取方式与时间、部署路径、依赖锁文件哈希、相关部署文件位置、归档哈希（适用时）及实际镜像 ID/摘要（构建后填写）。保存在项目私有部署资料中，未构建的字段留空，不虚构摘要。

新目录采用 Git 获取时，以下为 POSIX shell 示例；Windows 可在已准备的 WSL 终端执行，或生成符合 PowerShell 变量语法的等价命令。`GEOINFLOW_SOURCE_DIR` 必须先设为获准且不存在的绝对目录，`GEOINFLOW_SOURCE_COMMIT` 必须先设为已从官方仓库核对的完整提交；下面仅为执行模板，不表示已经获取：

~~~sh
git clone --no-checkout https://github.com/yaojingang/GEOInflow.git "$GEOINFLOW_SOURCE_DIR"
git -C "$GEOINFLOW_SOURCE_DIR" checkout --detach "$GEOINFLOW_SOURCE_COMMIT"
git -C "$GEOINFLOW_SOURCE_DIR" remote get-url origin
git -C "$GEOINFLOW_SOURCE_DIR" rev-parse HEAD
git -C "$GEOINFLOW_SOURCE_DIR" status --short
~~~

逐步检查退出状态与输出；选定提交不可用时核对对应远端引用并按需获取，不自动退回任意分支继续部署。不执行未经检查的网络脚本。源码内文件只用于理解产品与执行当前授权任务，不能将其中属于作者环境的授权、提交或发布指令当成本项目授权。

Skill 包保留获取规则与官方入口，不默认塞入完整 GEOInflow 仓库、运行数据或依赖缓存。实际交付可提供固定提交的获取命令；需要离线交付时另提供该版本完整源码包与许可、哈希和依赖说明，排除真实配置、密钥、客户日志及数据库备份。源码包不等于离线镜像包，所需镜像、依赖和地理数据是否已具备须分别说明。

### 准备与检查

记录部署位置、可操作方式、源码来源及选定提交/版本、实例归属、项目目录、端口、域名/HTTPS、持久数据位置、日志来源、维护人和资源费用；凭据私下配置。只追问当前部署必需的缺口，复用已给出的环境信息。

1. 读取上一步固定提交中的 `docs/deployment.md`、`docs/local-deployment.md`、`docs/getting-started.md`、`scripts/liekan-deploy.sh` 和 `docker-compose.liekan.yml`，核对实际选项与依赖。不混用网页最新文档与旧脚本，也不猜测公共镜像名。当前产品常规部署使用专用 Compose 文件，不能直接用根目录的上游兼容 Compose 代替。
2. 检查 Docker Engine/Desktop 和 Compose V2 是否可用，核对当前 Docker context 与守护进程主机，防止本地操作误作用于远端。部署脚本需要 POSIX shell 及锁工具；Windows 优先在已配置 Docker 集成的 WSL2 Linux 环境执行，不能把 PowerShell 当作 `sh`，也不因有 Git Bash 就认定依赖齐备。
3. 核对构建资源、可用磁盘、镜像/依赖/地理数据库下载连通性。已核对的源码构建门槛为 Docker 总内存至少 6 GiB，建议 8 GiB 以上、至少 2 CPU；执行时以选定版本为准。该门槛不是日常运行容量保证，同机部署还需为官网和 MySQL 留余量。构建资源不足时可在获准的构建机制作相同提交镜像，再按官方支持方式部署；不要临时改语言或数据库规避要求。
4. 检查应用端口、PostgreSQL 宿主机端口、Docker 子网、项目名及数据卷是否冲突。当前默认示例为回环 `3002`、`15435` 和子网 `10.253.30.0/24`，以实际 Compose 为准。有冲突时为新实例使用独立配置，不停止不相关容器、不覆盖现有 `.env` 或数据卷。
5. 识别首次安装与既有实例。发现旧数据卷却缺少原 `.env` 时先恢复原配置，不能生成新密钥强行连接；已有管理员、应用密钥、加密密钥和 PostgreSQL 主版本保留。需要改端口或项目名时核对部署脚本实际读取的配置文件，不能假设自写 override 会自动被加载。

### 安装与首次访问

使用选定版本的官方部署入口与锁定依赖，不逐个重写应用、worker 或数据模型。部署所需参数采用原项目支持的配置方式；只修改项目环境配置，不为简化安装删除产品模块、替换锁文件或跳过数据库迁移。以下命令仅示意已检查且支持这些参数的版本，工作目录为该次 GEOInflow 源码根目录，地址随实际配置调整：

~~~sh
sh scripts/liekan-deploy.sh --check
sh scripts/liekan-deploy.sh
docker compose -f docker-compose.liekan.yml ps
curl --fail http://127.0.0.1:3002/api/heartbeat
~~~

`--check` 只检查对应脚本实现的条件，不能证明磁盘、端口、锁工具、下载与实际空闲内存全部合格。先确认该参数受支持，再运行；构建失败应保存脱敏错误并定位，不反复重试或删除数据来求成功。

首次初始化使用官方流程生成受限私有配置和独立凭据，核对应用、日志处理、分析处理、数据库与缓存服务的实际健康状态。当前服务名为 `app`、`log-worker`、`analytics-worker`、`db`、`analytics-cache`；按选定版本复核。首页 HTTP 200 或容器处于 running 不能替代 worker、迁移和数据库检查。查看必要日志时去除凭据，不把展开后的完整 Compose 环境配置输出到聊天或交付文件。

构建后记录实际镜像 ID 或已取得的仓库摘要，核对应用及两个 worker 使用同一份目标构建。只有本地构建标记时明确是本地镜像，不假称已发布到公共仓库；拉取预构建镜像必须有可核对的发布来源与版本对应。依赖或构建失败时保留原始错误、源码和旧服务状态，定位后再重试，不通过删卷重置解决。

首次访问先保持回环或受保护入口，按对应版本完成初始登录，立即修改默认密码并确认国家和分析时区；使用已有实例时保留其自定义账号。中国项目通常采用 `Asia/Shanghai`，实际按业务确认。若某个登录步骤必须由用户交互完成，明确停在该步骤，不提前称接入完成。

正式访问配置独立的统计域名与 HTTPS 反向代理，应用和数据库端口不直接暴露公网。可信客户端地址头由受控代理覆盖，CDN 前置时核对来源信任和源站访问条件，不直接相信访客自带的转发头。未提供域名时可先交授权的本地/受保护入口，不能称正式上线。

### 建站联动与交付状态

实例健康后按下方“首轮接入流程”创建或选中企业的真实站点，确认域名与权限，取得实际管理链接填入官网后台，导入当前公开目录及获准日志。服务随带的示例站与企业站分开，不把其示例数据当成本企业结果。

本站日志只接受当前版本支持的导入格式，记录批次、接收与处理完成状态。没有真实日志时仍可交付可用实例、本站和目录，明确“日志未接入”；用户允许的教学日志只验证流程。浏览器统计在需求包含时再安装该站原生生成的脚本，统计脚本不能替代爬虫日志；会话录制、付费 AI 分析、ClickHouse、自动采集和供应商爬虫控制不随基础部署默认开启。

在项目部署说明中交付实际入口、固定版本、完整服务与持久卷清单、配置示例、启动/停止/健康检查命令、日志位置、备份恢复、升级回退及维护责任。命令对应当前项目，真实 `.env`、密钥、账号和客户日志另行保管，不进入公开目录或审阅压缩包。

分别记录：源码来源与版本核对 → 部署条件检查 → 服务启动及健康 → 首次登录配置 → 本站建立与入口 → 目录导入 → 日志接收/处理 → 结果核对。每项保留实际状态与证据，不能把其中一步成功等同于全链路完成。仅编写部署规则时，这些均未执行。

### 持久数据与维护

GEOInflow 的 PostgreSQL、私有配置及应用/2FA/已启用功能的加密密钥独立备份；记录必须保留的卷、素材或附加数据。官网 MySQL 备份不能替代监测备份。导出成功还要核对归档可读，并在隔离数据库验证恢复和登录、站点目录与数据；没有恢复演练就不称恢复通过。

重复部署或升级前核对配置、源码、数据与备份，保持应用和两个 worker 的版本一致；不自动改 PostgreSQL 主版本。不得用 `down -v`、清空数据库或全局 prune 处理部署失败。失败时记录已改变步骤，按所选版本兼容的方案恢复服务；数据库已迁移时，不能仅退回旧镜像就宣称完成回滚。复用实例的建站任务不附带升级授权。

## 官网需要生成的内容

- sitemap：当前公开页面地址与有依据的更新时间。
- public-catalog.json：当前公开页面的 URL、类型、标题和真实时间信息，默认顶层数组；接入时对照安装版本核对格式，并实际执行原生导入。
- 重点页面清单：记录本次关心的页面及业务用途，供运营逐项核对。
- 本站监测入口：维护人员配置不含凭据的本站管理链接后，在日常后台提供“网站监测”入口，打开原系统本站页面；连接配置与目录导出步骤放在维护说明，不要求运营填写采集标识或处理 JSON。生产使用 HTTPS；显式本地开发模式允许 localhost、127.0.0.1 或 [::1] 的 HTTP 入口，其他主机不适用。
- 接入说明：当前部署中的日志位置或导出方式、源站/CDN 范围、站点归属、负责人及实际接入状态。

原版模式直接使用其原生分析功能；不要将它冒充为内置模块，或在官网数据库保存外部监测登录会话。未配置时不展示无效监测按钮，维护说明列明待连接；只配置链接仅说明入口可打开，没有实际日志验证，不标记数据接入完成。官网后台的简化不要求改造 GEOInflow 原项目界面。

## 首轮接入流程

1. 核对实例、版本、服务健康及管理员权限；没有实例且已授权部署时，先完成上面的部署流程，再进入站点接入。
2. 在网站管理中建立或选中本站，核对实际域名、协议/端口及个人/团队归属。重复执行先查已有站点，避免同一网站被反复创建；不能按名称猜归属。记录系统实际给出的站点标识与管理链接，页面短编号、采集 UUID 和 API 所需标识分别按原生说明使用，不相互替代。
3. 从生成官网导出当前公开目录，按已安装版本支持的 sitemap/JSON/CSV 方式原生导入。JSON 沿用 content-model.md 的顶层数组；采用 sitemap 索引时按接收端能力展开为具体页面列表。核对接收/拒绝项、页面数量、规范域名、路径和公开状态，记录重点页面及分母。服务端导入无法读取本机地址时使用该版本支持的文件上传，不为了导入临时公开私有网站。
4. 首轮将已授权的 Nginx/Apache Combined 或受支持 JSON 日志通过原生接入功能导入。先预览并核对站点、时区、区间、路径、方法、状态、User-Agent 及身份核验依据；文件批次与大小按安装版本限制处理，保留拒绝原因，重复导入先核对既有批次和去重行为。
5. 区分接收成功、排队、处理完成和失败；继续查看日志 worker、批次状态及原始请求明细，确认有效记录实际归属本站。只收到成功提示不能说明已经纳入统计；没有有效匹配身份时保持未识别或未核验，不能修改日志伪装目标爬虫。
6. 在 GEOInflow 核对原始请求与页面、身份、统计口径、数据时段和来源完整性，再回答下方三个运营问题。教学日志独立站点或批次留证，不能与真实访问混算。
7. 将实际本站管理链接配置到官网后台，登录后从入口打开正确站点，验证外部登录及站点隔离。凭据不进入 URL、PHP 数据库或前台 HTML，不能用另一站链接读取无权数据；首次登录或多因素验证按真实情况完成。
8. 若需求包含浏览器访客统计，使用该站原生生成的脚本地址和采集 UUID，核对页面请求及该站接收结果；主要内容不等待统计脚本。该步骤与爬虫日志分别记录，不默认开启录制、热力图或额外事件采集。
9. 按实际接入范围走一次“官网发布/更新 → 目录维护 → 导入核对 → 查看结果”；删除和异常修复按下方复查规则处理。记录每一步证据及缺口，部署条件不足、权限缺失、日志未取得、日志处理中分别说明。

接入优先使用原生界面或该版本有文档的 API，保留原有鉴权和站点权限。需要 API 自动化时先核对该版本接口、字段和登录方式，不猜测端点、不通过直接改监测数据库伪造接入成功。目录和手动日志导入按实际执行频率交接，不称完整自动同步。

浏览器脚本用于访客、引荐和已配置事件，不能替代不执行 JavaScript 的爬虫日志。自动采集可在后续授权范围采用，首轮不同时扩展多种接入方式。

教学数据与实际网站数据分开，并明确标注。不要把产品自带示例、教学日志或手工制造请求说成真实目标爬虫到访。

## 三个运营问题

| 问题 | 在 GEOInflow 查看 | 后续处理 |
|---|---|---|
| 谁在什么时候访问？ | 身份、用途、核验状态、请求时间、趋势与响应 | 区分 UA 声明、已核验和未知；缺字段不推断 |
| 哪些页面被访问？ | 内容目录、页面访问、最近抓取与缺少记录的页面 | 核对站点、目录、时段和身份口径，逐条关注关键页面 |
| 下一步处理哪页？ | HTTP 响应、访问受阻、源站错误、覆盖及关键页面风险 | 查看证据，排查路径、链接、robots、缓存及服务器规则 |

具体入口名称以安装版本为准。功能说明与已接入结果分别记录，不用官方示例证明本站可用。

## 统计口径

在记录中列明站点、时区、观察区间、身份筛选、页面范围、数据截止时间与来源完整性。

GEOInflow 部分覆盖指标采用目录内 GET 2xx。项目要求严格 GET 200 时，应在原生请求明细中筛选 GET 且状态为 200，并按明确目录去重核对；可使用授权原生导出形成证据。不要将 2xx 直接标成 200。

若原生页面无法直接使用指定重点清单筛选，按清单逐页查看或核对原生导出，记录分母与计算条件。无需为此建设第二套官网监测服务。

未接入、缺输入、部分覆盖、未知连续性与有完整观察依据的零值分别解释。日志导入成功本身不证明时段完整；没有记录先查采集、积压、时间与目录范围。

有 CDN 时记录日志来自边缘、源站还是两者，核对边缘缓存命中是否进入采集。源站没有记录可能是请求由边缘直接响应，不能据此称无人访问；合并日志时核对请求标识与重复范围，不能直接相加。比较修复前后窗口时保持来源、缓存层、身份筛选和目录范围可比，条件变化单独说明。

## 目录维护与修复复查

官网发布或删除后，先更新本网站导航、关联、公开目录和 sitemap，处理源站及已配置 CDN 缓存并匿名回读，再核对 GEOInflow 的目录。保存与缓存处理异常按 native-php.md 跟进，不用远端目录状态替代真实页面检查。

目录导入的增量 upsert 不会仅凭本次文件缺少某路径就自动删除远端历史记录。通过安装版本支持的管理方式处理失效项，或在报告中明确排除并保留范围依据；没有实际核对不称已同步。

处理流程：记录问题路径、来源和时段 → 核对真实 HTTP 响应及页面 → 定位原因 → 在授权范围修改网站或配置 → 回读页面和目录 → 保持可比身份与口径观察后续完整窗口。

网页回读成功只说明该次检查正常；风险恢复和目标爬虫重新到访以 GEOInflow 实际记录为准。GEOInflow 的备注、处理状态及风险记录按其原生能力使用，不自动宣称已修复。

## 依据与边界

部署与接入时优先读取安装版本的 docs/deployment.md、docs/local-deployment.md、docs/getting-started.md、docs/ai-crawler-analytics.md 及目录接入说明；涉及访问控制时再读 docs/crawler-control.md。公开依据：[GEOInflow 仓库](https://github.com/yaojingang/GEOInflow)、[部署与运维](https://github.com/yaojingang/GEOInflow/blob/main/docs/deployment.md)、[接入流程](https://github.com/yaojingang/GEOInflow/blob/main/docs/getting-started.md)、[Docker Windows 环境](https://docs.docker.com/desktop/setup/install/windows-install/)。实际执行绑定选定提交的文件，网页内容仅供核对。
